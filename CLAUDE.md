# turnos_service

Los comandos se ejecutan desde la raíz de este repositorio.

## Requisitos

- Docker en ejecución: lo usan el compose y los tests.
- Un archivo `.env` creado a partir de `.env.example`, con `TURNOS_DB_PASSWORD` y `TURNOS_JWT_PRIVATE_KEY_LOCATION` completos, y las tres variables `TURNOS_CATEDRA_*` de la cuenta técnica. No se versiona. Sin las de la cátedra, el servicio arranca con un warning y sin integración. `TURNOS_CORS_ALLOWED_ORIGINS` es opcional: vacía, ningún navegador puede usar la API (decisión 007). `TURNOS_CATALOG_BASE_URL` apunta al servicio de catálogo; vacía, el servicio arranca con un warning y `GET /api/free-slots` responde `503` `CATALOG_UNAVAILABLE`. Los tiempos, reintentos, zona de atención (`TURNOS_ATTENTION_ZONE`, la comparten `availability` y `reservation`), antigüedad del caché y margen de seguridad de los holds (`TURNOS_RESERVATION_SAFETY_MARGIN`, 30 s) son opcionales y están comentados en `.env.example`; una variable vacía conserva el valor por defecto. El barrido de vencidos (T12) y la reconciliación (T13) son la excepción: `TURNOS_RESERVATION_SWEEP_INTERVAL` y `TURNOS_RESERVATION_RECONCILIATION_INTERVAL` (1 minuto) vacías, en `0`, negativas o mal escritas impiden arrancar, y `TURNOS_RESERVATION_SWEEP_ENABLED` y `TURNOS_RESERVATION_RECONCILIATION_ENABLED` vacías los apagan. `TURNOS_CATEDRA_OPERATIONS_INITIAL_LOGIN_WAIT` (2 minutos) es lo que espera la reconciliación de arranque al login técnico inicial. `TURNOS_DB_SOCKET_TIMEOUT` (segundos que se espera una respuesta de Postgres, 30 por defecto, D5 de T09) también es opcional, y es otra excepción: si se define vacía, la aplicación no arranca, porque la lee el driver de Postgres, que exige un entero. Kafka no lleva variables obligatorias: los servidores, los topics y el consumer group llegan con el login técnico; las `TURNOS_CATEDRA_KAFKA_*` (consumo, seguridad, reintentos y publicación) son opcionales. `TURNOS_E2E_KAFKA_CONSUMER_GROUP` es solo de la suite E2E (la aplicación no la lee) y tiene que terminar en `-e2e`. La suite normal de tests nunca lee el `.env` (simula catálogo y cátedra); solo la suite E2E (`-Pe2e`) lo lee.
- El par de claves RSA del JWT de los usuarios en `secrets/`, que no se versiona. Sin la clave privada, la aplicación no arranca (los tests generan su propio par). `docker compose up` lo genera solo la primera vez (servicio `turnos-keys`); para correr con `./mvnw` sin haber levantado el compose, se crea una sola vez a mano:

```bash
mkdir -p secrets
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out secrets/jwt-private.pem
openssl rsa -pubout -in secrets/jwt-private.pem -out secrets/jwt-public.pem
```

## Comandos

| Para | Comando |
| --- | --- |
| Levantar la base y la aplicación en contenedores (la primera vez genera las claves y construye la imagen) | `docker compose up -d --build` |
| Levantar solo Postgres de desarrollo, para correr la aplicación con `./mvnw`, y esperar a que esté listo | `docker compose up -d --wait turnos-db` |
| Levantar el sistema completo, con catálogo (necesita `../catalog_service` con su `compose.yaml`) | `docker compose -f compose.full-system.yaml up -d --build` |
| Ver el estado de los contenedores | `docker compose ps` |
| Correr la aplicación (necesita Postgres levantado) | `./mvnw spring-boot:run` |
| Correr todos los tests (Testcontainers crea su propio Postgres; no usan el compose) | `./mvnw test` |
| Correr solo la suite E2E, contra la cátedra real con las credenciales del `.env` (se saltea sin ellas) | `./mvnw test -Pe2e` |
| Correr una sola clase de test | `./mvnw test -Dtest=NombreDeLaClase` |
| Compilar desde cero y correr los tests | `./mvnw clean test` |
| Tests más reporte de cobertura de JaCoCo (`target/site/jacoco/jacoco.xml`), lo mismo que corre GitHub Actions | `./mvnw clean verify` |
| Apagar los contenedores conservando los datos | `docker compose down` |
| Apagar los contenedores y borrar los datos de la base | `docker compose down -v` |

## Datos del proyecto

## Docker

- `Dockerfile` en dos etapas: compila con el `./mvnw` del repo dentro de `eclipse-temurin:25-jdk`, sin tests (necesitan Docker), y ejecuta solo el jar en `eclipse-temurin:25-jre`, con un usuario sin privilegios. `.dockerignore` deja afuera `target/`, `.env`, `secrets/`, `*.pem`, `.git/` y `docs/`.
- `compose.yaml`: `turnos-db`, `turnos-keys` (de un solo uso: genera el par de claves en `secrets/` si falta; monta la carpeta del repo para crear `secrets/` con el usuario de la máquina, porque si Docker la creara al montarla quedaría a nombre de root) y `turnos-service` (espera a las dos). La app recibe el `.env` con `env_file`, y el compose cambia lo distinto dentro de Docker: `TURNOS_DB_HOST=turnos-db`, `TURNOS_DB_PORT=5432`, `TURNOS_JWT_PRIVATE_KEY_LOCATION=file:./secrets/jwt-private.pem` y `TURNOS_CATALOG_BASE_URL=${TURNOS_CATALOG_DOCKER_URL:-http://catalog-service:8080}`. `secrets/` se monta en solo lectura y la clave nunca entra a la imagen.
- **Permisos de la clave:** `secrets/` es `700` y la privada `600`, del usuario de la máquina. Por eso `turnos-keys` y `turnos-service` corren con `user: "${TURNOS_UID:-1000}:${TURNOS_GID:-1000}"`: con el usuario de la imagen (uid 999) la app no puede leer la clave y dice que no existe (comprobado el 2026-11-07). Los `secrets:` de Compose no lo resuelven: fuera de Swarm ignoran `uid`, `gid` y `mode` (Compose lo avisa) y montan el archivo con sus permisos.
- El volumen de la base tiene nombre fijo, `turnos_service_turnos-db-data` (el que Compose le había dado antes), para que sea la misma base si turnos se levanta solo o con el sistema completo. **`docker compose down -v` lo borra**, también desde otro proyecto que declare ese volumen; para borrar solo un volumen de prueba, `down` sin `-v` y `docker volume rm` con su nombre.
- `compose.full-system.yaml`: `name: full-system` e `include` de este `compose.yaml` y de `../catalog_service/compose.yaml`. Solo incluye: lo que conecta un servicio con el otro va en el `compose.yaml` de cada uno. Catálogo tiene un archivo igual. Requiere los dos repositorios uno al lado del otro, y no se puede levantar a la vez que un servicio solo (mismos puertos). Hasta que catálogo tenga su `compose.yaml`, falla al no encontrarlo.
- Comprobado el 2026-11-07, sin la cátedra (sus variables vacías) y con una base descartable: el build, la generación de claves (la segunda corrida no las toca), el arranque como uid 1000, `POST /api/register` `201`, `POST /api/authenticate` con JWT, `GET /api/free-slots` `503` `CATALOG_UNAVAILABLE` sin catálogo y `401` sin token. No se probó contra la cátedra desde el contenedor: la red del Kafka de la cátedra se superpone con la red por defecto de Docker; en la máquina de desarrollo gana la ruta más específica, pero falta la corrida real.

## Arquitectura

Se aplica la skill `hexagonal-vertical-slicing` (`documentacion/.claude/skills/hexagonal-vertical-slicing/SKILL.md`). Slices actuales:

| Paquete | Qué contiene |
| --- | --- |
| `turnos.user` | Usuarios finales: T01 (`POST /api/register`) y T02 (`POST /api/authenticate`, emite el JWT RS256). Además, las piezas que validan ese JWT (`infrastructure/security`, decisión 008), `ExistsUserByIdUseCase` (solo sí o no) y `GetUserNameUseCase` (solo nombre y apellido, en el tipo `UserName`), que usa `reservation` |
| `turnos.catedra` | Pasarela hacia la cátedra (única puerta). Sesión técnica (X01): login técnico al arrancar, estado en memoria, renovación a pedido. Consulta de ocupaciones (`GetOccupanciesUseCase`, T03), creación de holds (`CreateHoldUseCase`, T04), su confirmación (`ConfirmHoldUseCase`, T05) y la cancelación de una reserva (`CancelAppointmentUseCase`, T11, sobre `CatedraAppointmentClient`: piezas de "appointments", no de holds, donde se suma T13). Las reglas comunes de cada llamada (sesión, `401`, reintentos) viven en `application/support/CatedraOperationRunner` (decisión 011). Kafka (T07, decisión 014): consume el topic de acciones en `infrastructure/kafka`, el único lugar del servicio que conoce Kafka; el consumo arranca con el aviso de integración habilitada (`TechnicalIntegrationListener`) y cada evento entra por `CatedraEventService`, con un caso de uso por tipo (pedido de teléfono de T07 y resultado de T08, `AppointmentResult`), y sale por el puerto `CatedraEventHandler`, que implementa `reservation`. T06 publica en el topic de teléfono: `CheckTechnicalIntegrationUseCase` dice si hay integración (solo sí o no, para que el JWT técnico no salga del slice), y `SubmitAdditionalInformationUseCase` arma el envío y lo entrega al puerto `AdditionalInformationPublisher`. Hasta T03 se llamaba `integration` (decisión 009) |
| `turnos.catalog` | Pasarela hacia el servicio de catálogo (única puerta): `GetProfessionalUseCase` pide un profesional reenviando el JWT del usuario. Los reintentos viven en el adaptador HTTP; sin service, porque no tiene controller (decisión 009, P7 del PLAN de T03) |
| `turnos.availability` | T03 (`GET /api/free-slots`): cálculo de turnos libres, caché en memoria de ocupaciones y adaptadores `infrastructure/gateway` hacia `catalog` y `catedra` |
| `turnos.reservation` | Proceso de reserva. T04 (`POST /api/reservation-processes`): bloquea un turno con un hold de la cátedra y guarda el proceso en `HELD` (tabla `reservation_processes`, migración `V2`). T05 (`POST /api/reservation-processes/{id}/confirm`): confirma el hold y pasa el proceso a `WAITING_FOR_PHONE`; marca para reconciliar (`needs_reconciliation`, migración `V3`) cuando no se sabe si la cátedra confirmó. T07 (pedido de teléfono de la cátedra, por Kafka): `ProcessPhoneRequestUseCase` guarda el `requestEventId` y el vencimiento, y pasa un `HELD` a `WAITING_FOR_PHONE`; registra el evento en `processed_events` en la misma transacción (`TransactionRunner`, migración `V4`). T08 (resultado de la cátedra, por Kafka): `ProcessReservationResultUseCase` recibe un `ReservationResult` (cinco variantes) y confirma, rechaza el teléfono, vence, invalida o cancela el proceso (migración `V5`); un evento que no se aplica en ese estado solo registra su `eventId`. T06 (`POST /api/reservation-processes/{id}/phone`): valida el teléfono antes de la base (`ReservationPhoneNumber`), guarda `PHONE_SUBMITTED` y recién después publica, todo con el candado; si no se pudo publicar, vuelve a `WAITING_FOR_PHONE` y marca (migración `V6`). T09 (`GET /api/reservation-processes/{id}`): lee sin candado y, solo si el vencimiento exige cerrar o marcar, toma el candado, vuelve a leer y guarda. T10 (`GET /api/reservation-processes`): solo lee, sin candado; la consulta deja afuera los `HELD` y `WAITING_FOR_PHONE` vencidos, que resuelve quien los use o T12, y ordena y pagina en la base (`ReservationListCriteria`, `ReservationProcessPage`, índice por usuario en la migración `V7`). T11 (`POST /api/reservation-processes/{id}/cancel`): un `CONFIRMED` se cancela en la cátedra; un `HELD` o `WAITING_FOR_PHONE` sin marca se abandona solo en turnos (`abandon`, decisión 015); todo con el candado. T12 (por tiempo, sin endpoint): `OverdueProcessSweepScheduler` llama a `ExpireOverdueProcessesUseCase`, que busca los vencidos de todos los usuarios sin candado (`findOverdue`) y resuelve cada uno con el candado de su usuario y volviendo a leerlo; es local. T13 (por tiempo, sin endpoint): `ReconciliationScheduler` llama a `ReconcilePendingProcessesUseCase`, que busca los marcados (y, hasta completar la revisión de arranque, los abiertos sin marca: `findToReconcile`), consulta a la cátedra sin candado por `AppointmentFinder` (implementado por `CatedraAppointmentAdapter`, que entra a `FindAppointmentUseCase` de `catedra`), y aplica la respuesta con el candado y volviendo a leer; una cátedra no disponible corta el ciclo (decisión 016). Adaptadores `infrastructure/gateway` hacia `user` (`UserDirectoryAdapter`), `catalog` y `catedra` (`CatedraHoldAdapter`, `CatedraAppointmentAdapter`, `CatedraPhoneAdapter` y `CatedraEventAdapter`, que implementa el puerto de `catedra` para recibir sus eventos). Un proceso abierto por usuario: índice único parcial (decisión 012) y un candado por usuario compartido por bloquear, confirmar, informar el teléfono, cancelar, procesar los eventos de la cátedra y cerrar o marcar un vencido al consultar o en el barrido, y reconciliar (`application/support/UserOperationLock`, decisión 013) |
| `turnos.config` | Configuración transversal, sin lógica de negocio: `SecurityConfig`, `SecurityProblemHandler`, `CorsProperties`, `ApiExceptionHandler`, `JpaAuditingConfig`, `ClockConfig`, `SchedulingConfig` |

### Criterios de diseño acordados con el usuario

- Cada slice tiene solo las piezas que alguien usa; no se copian piezas de otro slice para que se parezcan (por ejemplo, un service sin controller). El modelo empieza con los datos que usa el caso de uso actual.
- En los casos de uso siguientes se amplían los archivos existentes (sumar `date` o `expiresAt` a `Occupancy`, nombre y categoría a `Professional`) en lugar de crear piezas paralelas, y se actualizan los tests afectados.
- La lógica de sesión técnica, renovación ante `401` y reintentos ya está extraída en `catedra/application/support/CatedraOperationRunner` (T04, decisión 011). Toda operación nueva con la cátedra (T11, T13) la usa, como la confirmación de T05; no se copia. Reintentar un `POST` que crea algo no es seguro: solo se repite lo que seguro no llegó (ver "Cómo usar la integración con la cátedra").
- Las transiciones del proceso de reserva viven en el modelo (`ReservationProcess`: `confirm`, `expire`, `expireIfOverdue`, `resolveOverdue`, `markForReconciliation`, `acceptPhoneRequest`, `submitPhone`, `revertPhoneSubmission`, `confirmReservation`, `rejectPhone`, `closeAsExpired`, `invalidate`, `cancel`, `abandon`, `reconcileWith`, `reconcileWithoutRecord`), que valida que sean válidas; los casos de uso no cambian el estado con setters. `confirm` es la confirmación inicial del hold (T05); `confirmReservation`, la reserva confirmada (T08); `resolveOverdue` aplica la regla completa del vencido, cerrar o marcar según el estado, y `needsOverdueResolution` dice si queda algo por hacer (T09; T10 y T12 necesitan la misma regla). Todo cierre pasa por un solo método, que borra el motivo de rechazo (solo tiene valor en `WAITING_FOR_PHONE`, D7 de T08) y apaga la marca de reconciliación (un proceso cerrado no tiene nada que reconciliar, dominio regla 9); `invalidate` la vuelve a encender. `reconcileWith` y `reconcileWithoutRecord` aplican la tabla de T13 (contrato §4.2.6) y devuelven un `ReconciliationOutcome`; son la única salida de un `INVALID` a otro estado final, y nunca reabren un cerrado (D2 de T13, `canBeReconciled`). Toda operación sobre los procesos de un usuario toma `UserOperationLock` (decisión 013), también la que llega por Kafka, con el dueño del proceso (T07 D2): un candado distinto no excluiría a las demás, y sin él una escritura pisaría a la otra (cada `update` reescribe el proceso entero). No hay control de versión (P5 de T07). **Excepción (D2 de T09):** una consulta lee sin candado, porque se repite cada pocos segundos y no debe esperar a otra operación; si tiene que escribir, toma el candado y vuelve a leer antes de decidir. Esa relectura ve datos frescos solo porque `spring.jpa.open-in-view` está en `false`: con `true`, Hibernate devuelve el objeto de la primera lectura en el mismo request y se pisaría un resultado de la cátedra (P2 de T09). T10 no toma el candado porque no escribe (D2 de T10). La regla del vencido queda en `ReservationProcess.hasExpired` y en las consultas `LISTABLE` y `findOverdue` de `JpaReservationProcessRepository`: si cambia una, hay que cambiar las otras, y `aProcessWaitingForTheUserIsListedExactlyUntilTheModelSaysItExpired` y `anOpenProcessIsFoundAsOverdueExactlyWhenTheModelSaysSo` lo detectan. La búsqueda solo trae candidatos: decide `resolveOverdue` con el proceso releído. **T12 cierra también los `HELD` y `WAITING_FOR_PHONE` marcados (D1 de T12):** el margen de seguridad hace muy improbable perder una reserva, y ese caso raro es una limitación aceptada. Qué estados se listan: `ReservationStatus.isListable` y el `@Pattern` de `ReservationProcessListRequest`, que un test obliga a mantener iguales.
- Todo lo que entra a un slice desde afuera (un controller, el consumidor de Kafka, un gateway que implementa el puerto de otro slice) entra por su service, nunca directo a un puerto (skill §5.3, P10 de T07).
- Un `update(id, modelo)` de un adaptador de persistencia exige el modelo al entrar con `Objects.requireNonNull`: el mapper de la skill devuelve `null` si recibe `null`, y SonarQube marca el acceso a la entidad que sigue (como en `JpaReservationProcessRepositoryAdapter.update`).
- Las restricciones de Bean Validation llevan siempre su mensaje propio en inglés: el mensaje por defecto cambia con el idioma del servidor o el `Accept-Language` del cliente (MockMvc usa inglés por defecto y no lo detecta).

### Excepciones a la skill autorizadas por el usuario

Cada una lleva un comentario corto en el código. Una excepción nueva se consulta antes y, si es compleja, se documenta en `docs/decisiones/`.

- Paquete `turnos.config` fuera de los slices, para configuración transversal.
- `@RestControllerAdvice` global (`ApiExceptionHandler`): da formato `problem+json`, `VALIDATION_ERROR` con `fieldErrors` e `INTERNAL_ERROR`. Decisión 003.
- Rutas bajo `/api` (las del contrato), en lugar de `/{entities}`.
- Paquetes de infraestructura además de `persistence` y `web`: `infrastructure/security` (adaptadores de seguridad, decisiones 001 y 004), `infrastructure/client` (clientes HTTP hacia sistemas externos), `infrastructure/startup` (disparadores al arrancar), `infrastructure/gateway` (adaptadores de salida que implementan un puerto propio llamando al puerto de entrada de otro slice; el único lugar donde un slice importa a otro, decisión 009), `infrastructure/config` (propiedades y `@Configuration` propias de un slice: `availability` y `reservation`), `infrastructure/scheduling` (en `reservation`: disparadores por tiempo, que solo llaman al service; P1 de T12) e `infrastructure/kafka` (en `catedra`: todo lo de Kafka, decisión 014).
- `reservation/infrastructure/gateway/CatedraEventAdapter` implementa un puerto de salida **de `catedra`** (`CatedraEventHandler`) y entra a `reservation` por su service: al revés que los demás gateways, para que `catedra` entregue sus eventos sin conocer a `reservation`. Un solo puerto y un solo gateway para los seis eventos (P2 de T08); los casos de uso siguen separados. Solo usa el puerto y el modelo de `catedra`; la dependencia sigue siendo `reservation` → `catedra` (P1 de T07).
- Paquete `catedra/application/support/` con `CatedraOperationRunner`: no es un caso de uso ni se ofrece a otros slices, porque maneja el JWT técnico (decisión 011).
- Paquete `reservation/application/support/` con `UserOperationLock`: un candado por usuario en memoria, compartido por los casos de uso del slice; vale para una sola instancia del servicio (decisión 013).
- La clave primaria de `reservation_processes` es el `reservationProcessId` de la cátedra (`VARCHAR(255)`), no un `Long id` autogenerado. `ReservationProcessEntity` implementa `Persistable` para que Spring Data no haga un `SELECT` antes de cada `INSERT` (decisión 012). Tiene clave foránea a `users` (`fk_reservation_processes_user`) e índice único parcial `ux_reservation_processes_one_open_per_user`; el adaptador distingue cuál rechazó un `INSERT` por el nombre. Lo mismo para `processed_events`: la clave es el `eventId` de la cátedra y `ProcessedEventEntity` también implementa `Persistable` (T07).
- Puertos de salida para capacidades técnicas, no solo `{Entity}Repository`: `PasswordHasher`, `TokenIssuer`, `TechnicalLoginClient` (decisión 001), `TechnicalIntegrationListener` (el aviso de integración habilitada) y `TransactionRunner` (ejecutar un bloque en una transacción, implementado con `TransactionTemplate` en `SpringTransactionRunnerAdapter`; P4 de T07). El caso de uso nunca conoce la librería.
- Repositorios en memoria en `persistence/adapter`, sin base de datos: `InMemoryTechnicalSessionRepositoryAdapter` y el caché de ocupaciones `InMemoryOccupancyCacheAdapter` (se limpia solo con un `@Scheduled` cada minuto).
- `record` inmutables en lugar de clases Lombok cuando el objeto se lee en paralelo mientras se reemplaza: `TechnicalSession`, `TechnicalIntegration`, `TechnicalLoginResult` (interfaz sellada). Sus `toString` ocultan el JWT.
- `record` inmutable para un dato validado: `ReservationPhoneNumber`. Solo se crea validado, sin setters, y su `toString` oculta el número (T06).
- Resultados sellados de `record` para lo que devuelve un sistema externo, en lugar de excepciones: `ProfessionalResult` (`catalog`), `CatedraResponse<T>` (lo que devuelve cada cliente HTTP de la cátedra en un intento, decisión 011), `OccupanciesResult`, `HoldResult`, `HoldConfirmationResult`, `AppointmentCancellationResult`, `AdditionalInformationSubmissionResult`, `CatedraEventResult` y `AppointmentResult` (`catedra`), `ReservationResult` (`reservation`), y `AppointmentAction` (lo que resulta de leer un mensaje de Kafka, en `catedra/infrastructure/kafka`). Políticas como `record` del dominio: `TechnicalLoginPolicy`, `CatedraOperationPolicy`, `AvailabilityPolicy`, `ReservationPolicy`.
- Varios formatos de request o response en un slice, con nombres propios (`AuthenticateRequest`, `TokenResponse`): los nombres de la skill salen del ejemplo `product`.
- `@Configuration` dentro de la infraestructura de un slice para armar beans técnicos que usa otra parte del servicio por una interfaz de Spring o el propio slice: `CatedraClientConfiguration`, `JwtValidationConfiguration` (decisión 008), `AvailabilityConfiguration` y `ReservationConfiguration`.
- `ReservationProcessController` lanza `ErrorResponseException` (con `ProblemDetail` y `code`) en lugar de `ResponseStatusException`, porque algunos errores llevan encabezados: `WWW-Authenticate: Bearer` en el `401` de un usuario inexistente y `Retry-After` en `HOLD_NOT_SAVED` (P7 del PLAN de T04).
- `ReservationProcessRequest.professionalId` es `BigDecimal` (acepta `1.0` o `"15"` como enteros y da un solo error en `fieldErrors` para un número enorme), con constructor de todos los campos escrito a mano y setter que quitan los ceros decimales: Jackson 3 construye el DTO con ese constructor, no con el setter (P8 del PLAN de T04).

### Comentarios y nombres en el código

- El código, sus comentarios y los nombres de los tests no citan documentos: ni el contrato, ni el anexo de la cátedra, ni el enunciado, ni secciones, reglas o IDs de requisitos (`§`, `RF-`, `CA-`). Un comentario explica el porqué o avisa algo, con palabras propias. Un test se nombra por el comportamiento que comprueba (no "según el contrato").
- Las referencias a documentos van en `docs/sdd/` (SPEC, PLAN y TASKS) y en `docs/decisiones/`.

### Errores HTTP

- El controller atrapa las excepciones de su slice y relanza `ResponseStatusException` con el estado y la propiedad `code` del contrato (por ejemplo `USERNAME_ALREADY_EXISTS`, `INVALID_CREDENTIALS`). Excepción: `reservation` usa `ErrorResponseException` (ver arriba).
- Si el JSON está bien escrito pero un campo no se puede convertir (`"abc"` en un número, una fecha imposible), `ApiExceptionHandler` responde `VALIDATION_ERROR` con ese campo en `fieldErrors` e `invalid value`; un JSON mal escrito responde sin `fieldErrors`.
- `ApiExceptionHandler` solo da formato; no importa nada de los slices.

### Seguridad

- `SecurityConfig`: sin sesión (`STATELESS`), CSRF desactivado (decisión 006, marcado como falso positivo en SonarQube), CORS (decisión 007) y validación del JWT (decisión 008). Una sola lista de rutas públicas, `POST /api/register` y `POST /api/authenticate`, que usan el `permitAll` y el lector del token: en esas rutas el encabezado `Authorization` se ignora aunque sea inválido. El resto exige un JWT válido con al menos un rol de `Authority`.
- JWT del usuario: RS256 con la clave privada de `secrets/` (`turnos.jwt.private-key-location`); `JwtSigningKeys` la carga una vez y obtiene la pública para la firma y la validación. Claims exactos: `sub`, `auth`, `iat`, `exp` (decisión 004).
- Validación (`user/infrastructure/security/JwtValidationConfiguration`): solo RS256 con la clave propia, `exp` obligatorio y sin tolerancia de reloj, `sub` solo dígitos dentro del rango de un `Long`. Sin estado: no consulta la base. `config` recibe el decodificador, el conversor de roles y la regla de roles por interfaces de Spring, sin importar el slice.
- Rechazos (`SecurityProblemHandler`): `401` y `403` en `problem+json` con `title`, `status`, `detail` e `instance`, sin `code`, con un único cuerpo por estado; el `401` lleva `WWW-Authenticate: Bearer` sin el motivo. Spring Security 7 agrega la autoridad `FACTOR_BEARER` a toda autenticación por token: no es un rol.
- CORS: orígenes exactos en `TURNOS_CORS_ALLOWED_ORIGINS`, separados por comas, vacía por defecto. Nunca `*`. Un origen no permitido recibe `403` `Invalid CORS request`.

### Cómo obtiene la identidad un controller (desde T03)

- El controller recibe el `Jwt` validado (`@AuthenticationPrincipal Jwt jwt`) y pasa al service valores simples: `Long.valueOf(jwt.getSubject())` como id del usuario y, si hay que reenviar el token a catálogo (C06), `jwt.getTokenValue()`. El service y el caso de uso no conocen Spring Security.
- La identidad nunca sale de un parámetro, del cuerpo ni de otro encabezado.
- Puede cambiar: si la extracción se repite demasiado o la identidad suma datos, se revisa con un paquete `shared` con un tipo para la identidad (decisión 008).

### Tareas programadas (desde T12)

- `@Scheduled` con espera fija (`fixedDelayString`): corre al arrancar, y la siguiente corrida empieza cuando termina la anterior, por eso no se solapa consigo misma, tampoco con hilos virtuales. **Con frecuencia fija e hilos virtuales sí se solapa** (comprobado en TASK-05 de T12). Sin demora inicial, la primera corrida puede adelantarse al login técnico y al consumo de Kafka.
- Si una excepción sale de una tarea, Spring la registra como error inesperado y la sigue programando (comprobado en TASK-07 de T12). Atraparla da un mensaje propio, no la continuidad.
- Las tareas tienen dos hilos (`spring.task.scheduling.pool.size: 2`, desde T13): la reconciliación puede esperar a la cátedra, y así no demora al barrido de T12 ni a la limpieza del caché de ocupaciones (D8 de T13, comprobado por `aSlowReconciliationDoesNotDelayTheOverdueSweep`).
- Las tareas arrancan antes que el login técnico inicial, que corre al `ApplicationReadyEvent`: la sesión empieza en `CONNECTING`. Una tarea que llama a la cátedra al arrancar usa `CatedraOperationRunner.runAfterInitialLogin`, que espera ese login con tope (P1 de T13); `run` responde enseguida "no disponible".

### Cómo usar la integración con la cátedra (desde T03)

- En cada operación, pedir la sesión con `GetTechnicalSessionUseCase` (JWT técnico e integración). Nunca guardar una copia en un campo: así siempre se usa la última.
- Si la cátedra responde `401`, llamar a `RenewTechnicalSessionUseCase.renewTechnicalSession(jwtRechazado)` y repetir la operación una sola vez con la sesión que devuelve; si devuelve vacío, la integración no está disponible (según el contrato, `503` `SERVICE_DEGRADED`).
- Desde T04 eso lo hace `CatedraOperationRunner.run(nombreDeLaOperacion, jwt -> cliente.llamar(..., jwt))`; un caso de uso de `catedra` no pide la sesión a mano. Para una operación nueva: un cliente HTTP en `infrastructure/client` que hace **un solo intento** y devuelve `CatedraResponse<T>`; el caso de uso llama al runner y traduce la respuesta a su propio resultado sellado (como `CreateHoldUseCaseImpl` → `HoldResult`).
- Cómo clasifica el cliente: `Answered` (respuesta definitiva, éxito o rechazo de negocio), `TokenRejected` (`401`), `ConfigurationError` (`403` `STUDENT_INTEGRATION_NOT_FOUND`), `Unavailable` (seguro que no llegó: conexión rechazada, timeout de conexión, host desconocido, `503`; el runner reintenta), `Uncertain` (pudo haber llegado: timeout de respuesta, corte durante la respuesta, `500`; no se reintenta) y `Failed` (no previsto). Una consulta trata todo como `Unavailable`. Una operación que crea algo distingue `Uncertain` si repetirla puede dañar (el hold: ver `CatedraHoldClientAdapter.wasNotSent`); si la cátedra detecta el repetido, todo es `Unavailable` y se reintenta (la confirmación: un intento ya procesado vuelve como `409` `RESERVATION_PROCESS_ALREADY_CONFIRMED`, D1 de T05; la cancelación: cancelar lo ya cancelado responde lo mismo, T11).
- `runAfterInitialLogin` (desde T13) es la variante para tareas programadas: si el login inicial está en curso, lo espera hasta `turnos.catedra.operations.initial-login-wait` y sigue como `run`. Las operaciones de los usuarios usan `run` y nunca esperan.
- El control de los logins (uno a la vez, intervalo mínimo de 60 s, error de configuración sin reintentos) vive en `catedra` (decisión 005). Los demás slices nunca llaman al login de la cátedra.
- Usar `catedra` desde otro slice es una dependencia entre slices: se decide con el usuario (skill §9). El otro slice declara su propio puerto de salida y lo implementa un adaptador en su `infrastructure/gateway`, que llama al puerto de entrada de `catedra` (como `availability/infrastructure/gateway/CatedraOccupancyAdapter`).
- Reglas de la cátedra comprobadas con respuestas reales (grabadas en `src/test/resources/catedra/`, ver su `README.md`): el `401` llega sin cuerpo ni `Content-Type`; un profesional inexistente da `200` con lista vacía; los errores `problem+json` traen además `type`, `message` y `path`; un hold dura 10 minutos y sus ids (`process-…`, `hold-…`) tienen 41 y 44 caracteres; una ocupación `HELD` llega con `startTime` `HH:mm:ss` y `expiresAt`. **Cancelar un proceso en `HELD` responde `404` `RESERVATION_NOT_FOUND`, y en `WAITING_FOR_PHONE`, `409` `RESERVATION_NOT_CANCELLABLE`**: por eso T11 los abandona solo en turnos (decisión 015). **Acepta otro hold de otro turno con el primero activo, y rechaza el turno todavía tomado** (E2E de T11, 2026-11-04). Cancelar un `CONFIRMED` no se probó contra la cátedra real, porque no se llega a ese estado mientras no publique por Kafka. **Confirmar no extiende el vencimiento:** la cátedra devuelve el mismo `expiresAt` del hold. **Un hold vencido responde `404` `HOLD_NOT_FOUND`, no `HOLD_EXPIRED`** (T05 lo trata como vencido si su `expiresAt` ya pasó, D8). La consulta de ocupaciones no informa las reservas que esperan el teléfono (`PHONE_PENDING`), aunque la cátedra sí las tiene en cuenta al crear un hold (el usuario decidió no tratarlo). **El listado de reservas (`GET /api/appointments`) responde `500` a todo pedido con `from` y `to`**: T13 filtra solo por `externalPatientId` y recorre las páginas (D1 de T13). Sin fechas funciona por paciente, por estado y paginado; una reserva recién confirmada figura de inmediato en `PHONE_PENDING`, una vencida sin teléfono en `FAILED`, y los holds no aparecen (2026-11-05). **Los profesionales cambian:** el 201 estuvo deshabilitado el 2026-11-05 (`400` `PROFESSIONAL_DISABLED`) y el 2026-11-06 volvió habilitado con otra categoría; para pruebas reales se elige uno habilitado desde el snapshot. Toda grabación nueva se limpia (JWT, contraseña de Redis, hosts, `groupId`) antes de versionarla.

### Cómo usar Kafka de la cátedra (desde T07)

Los conceptos, la configuración y todas las decisiones están en `docs/decisiones/014-kafka-con-la-catedra.md` (documento vivo: se actualiza con cada decisión de Kafka).

- **Nada de Kafka fuera de `catedra/infrastructure/kafka`**: ni tipos, ni nombres. El dominio y la aplicación hablan de "un pedido de la cátedra" y de "la integración se habilitó".
- El consumo no se configura al arrancar: `KafkaConsumerManager` lo arma por programa con los datos del primer login exitoso (`TechnicalIntegrationListener`) y conserva esos datos hasta reiniciar; un login posterior con otros datos solo deja un warning. Recibe el oyente con `ObjectProvider`: recibirlo al crearse cierra una dependencia circular entre beans (login → manager → oyente → `reservation` → bloqueo de T04 → login).
- Un mensaje: `AppointmentActionListener` → `AppointmentActionReader` (formato de la cátedra; lo inválido se descarta con su motivo en el log) → `CatedraEventService` → caso de uso de `catedra` → `CatedraEventHandler` → `CatedraEventAdapter` → `ReservationService`.
- El lector exige y convierte solo lo que cada tipo de mensaje usa (D8 y P3 de T08): las fechas, los instantes y los números llegan al DTO como texto. Un valor mal escrito en un campo que el tipo no usa no descarta el mensaje.
- **Un valor que la base rechaza frena a todos los mensajes siguientes**, porque se trata como una falla de la base. Por eso el lector descarta un `eventId`, `reservationProcessId` o `holdId` de más de 255 caracteres o con el carácter nulo, y el modelo recorta `reason` a 500 y le quita ese carácter (RF-17 de T08). Todo campo nuevo que llegue de Kafka y se guarde necesita lo mismo.
- Una lectura de la base también traduce su falla a `ReservationNotSavedException`: si no, con la base caída el mensaje se descartaría en lugar de reintentarse (TASK-12 de T08). Un mensaje se confirma cuando termina sin error (`AckMode.RECORD`); `CatedraEventNotSavedException` (falla de la base) se reintenta sin fin con la pausa, sin confirmar (los siguientes esperan); otro error se reintenta pocas veces y se descarta con un error grave (`MessageRetryBackOff`).
- Idempotencia: cada evento procesado queda en `processed_events` en la misma transacción que el cambio del proceso; un evento ya registrado no repite nada. Un resultado que no se aplica en ese estado también se registra (T08); un pedido de teléfono en esa situación no (T07).
- **Publicar (desde T06, decisión 014 §3.15 a §3.18):** `KafkaAdditionalInformationPublisher` usa `KafkaProducer` directo, creado en el primer envío, y conserva la dirección hasta reiniciar, como el consumo; el topic y el `groupId` son los de la sesión vigente. Hace sus propios intentos (`turnos.catedra.kafka.publish`, tope de 10 s) y deja cada fallo en el log; lo que no es reintentable, como un rechazo de credenciales, corta enseguida. No usa `CatedraOperationRunner`, que entrega un JWT que Kafka no necesita. Sin configurar `max.block.ms` y sus pares, el cliente bloquea hasta un minuto con el candado tomado.
- **Lo que se publica lleva un dato personal:** el teléfono no va a logs ni a respuestas. `ReservationPhoneNumber` oculta su `toString`, y `AdditionalInformationSubmission`, `PhoneSubmissionRequest` y `ReservationProcess` no generan uno. De un error no previsto al publicar o guardar se registra solo el tipo.
- **Un timeout no prueba que el mensaje no haya salido.** Un intento vencido puede llegar cuando Kafka vuelve, ya con el proceso de nuevo en `WAITING_FOR_PHONE`: una confirmación se aplica y un rechazo se ignora (014 §3.15). En los tests, un mensaje así aparece después, por eso se filtra por su instante.
- **Limitación aceptada (D1 de T06):** una caída entre guardar y publicar deja `PHONE_SUBMITTED` sin nada publicado. No se cierra por reloj: T12 solo lo marca, y T13 lo cierra como `EXPIRED` cuando la cátedra lo da por `FAILED`; mientras tanto, ese usuario recibe `OPEN_PROCESS_EXISTS` al bloquear otro turno.
- T13 cumple la condición de D5 de T08 (limitar el paso 6 a procesos abiertos): un cerrado marcado nunca se reabre (D2 de T13).
- Verificado contra el Kafka real (TASK-02 y TASK-12 de T07): `PLAINTEXT` sin credenciales, sin control de acceso (se ven los topics de todos: el servicio usa solo los de su `integration`), 1 partición, 7 días de retención, cualquier nombre de consumer group. **La cátedra publica en el topic de acciones desde el 2026-11-04** (hasta entonces estaba vacío; ese día publicó juntos los mensajes atrasados, con su `occurredAt` original). El E2E del 2026-11-06 hizo el recorrido completo: pedido de teléfono, teléfono publicado y consumido por la cátedra, `CONFIRMED`, cancelación y su evento. El formato es el del anexo, con instantes con nanosegundos y `reason` en `null` cuando no hay motivo; la clave es el `reservationProcessId` y no hay headers. Los mensajes reales están en `src/test/resources/catedra/kafka/*-real.json`; los armados desde el anexo siguen para los tipos que la cátedra no publicó (rechazo del teléfono e inválido) y para variar campos (decisión 014 §4).
- Las pruebas contra el Kafka real nunca usan el consumer group del servicio y las corre el usuario.

### Cómo usar catálogo (desde T03)

- Pedir el profesional con `GetProfessionalUseCase.getProfessional(professionalId, jwt.getTokenValue())`. Devuelve `Found`, `NotFound`, `Rejected` (`401`/`403` al token reenviado: error interno), `Unavailable` (después de los reintentos, o sin URL válida) o `Failed` (respuesta no prevista).
- Desde otro slice, por un puerto propio y un adaptador en `infrastructure/gateway` (como `CatalogAgendaAdapter` en `availability` y `CatalogProfessionalAdapter` en `reservation`). `Professional` trae nombre, apellido y nombre de la categoría; el `enabled` de la categoría no se lee, porque solo cuenta el del profesional.

## Tests

- La suite normal de Maven nunca lee el `.env` local: el `pom.xml` apunta `turnos.env-file` a un archivo inexistente (propiedad `tests.env-file`). Nunca usa las credenciales reales ni llama a la cátedra real. Solo la suite E2E (`-Pe2e`) lee el `.env` y habla con la cátedra real.
- `TestcontainersConfiguration`: Postgres 18 y la clave del JWT de test (`TestRsaKeys`, generada en cada corrida). Lo importan todos los tests que levantan la aplicación.
- Kafka en los tests (decisiones 010 y 014): Surefire pasa `turnos.catedra.kafka.enabled=false` a todos los tests, también en `-Pe2e`, porque la cátedra simulada informa servidores inventados. Los tests de Kafka lo encienden con sus propiedades y usan `KafkaTestContainer` (`apache/kafka:4.2.1` en Docker, compartido por la suite; `pause`/`unpause` para simular un Kafka caído) y `KafkaTestTopic` (un topic y un consumer group propios del test: publica como la cátedra y dice hasta dónde se confirmó). `FakeCatedraServer.provisionedLoginResponse` tiene una variante con el Kafka del contenedor, para que el consumo arranque como en producción (`PhoneRequestKafkaIntegrationTest`, `ReservationResultKafkaIntegrationTest`). `DatabaseDownKafkaIntegrationTest` pausa su propio contenedor de Postgres: una falla simulada al escribir no muestra lo que pasa con una base caída de verdad, donde lo primero que falla es una lectura. `PhoneSubmissionKafkaIntegrationTest` lee del topic de teléfono lo que publica el servicio (`KafkaTestTopic.messages()`), congela Kafka con los tiempos reales de publicación y falla a pedido sobre la base real con `ControllableProcessRepository`. Los tests de T08 dejan el proceso en `PHONE_SUBMITTED` escribiendo en la base como estado de partida; su recorrido completo usa el endpoint de T06. `KafkaAdditionalInformationPublisherTest` usa un `MockProducer` para lo que Kafka en contenedor no puede provocar, como un rechazo de credenciales.
- El barrido de T12 en los tests: Surefire pasa `turnos.reservation.sweep.enabled=false` a todos los tests, también en `-Pe2e`, porque cerraría los procesos que preparan. `OverdueSweepIntegrationTest`, `OverdueSweepAtStartupIntegrationTest` y `DatabaseDownOverdueSweepIntegrationTest` lo encienden con sus propiedades y llevan `@DirtiesContext`: en el caché de contextos seguiría corriendo durante el resto de la suite. `OverdueProcessSweepSchedulerTest` prueba el disparador con `ApplicationContextRunner`, sin base. Para tener un proceso guardado antes de arrancar, un bean con `@DependsOn("flywayInitializer")`: las tareas empiezan después de crear todos los beans.
- La reconciliación de T13 en los tests: Surefire pasa `turnos.reservation.reconciliation.enabled=false` a todos los tests, porque consultaría la cátedra simulada y cambiaría los procesos que preparan. `ReconciliationIntegrationTest` y `ReconciliationAtStartupIntegrationTest` la encienden y llevan `@DirtiesContext`; `ReconciliationTurnedOffIntegrationTest` comprueba que apagada no consulta. `ReconciliationSchedulerTest` prueba el disparador y, cargando `application.yaml` con `ConfigDataApplicationContextInitializer`, los dos hilos de tareas. Un doble que se configura antes de arrancar el contexto (`withBean`), porque la primera ejecución corre apenas arranca.
- `TestSecurityConfiguration`: la seguridad real (cadena, validación, claves y CORS) con la clave de test, para los `@WebMvcTest`. Los tests web la importan en lugar de `SecurityConfig`.
- `TestTokens`: arma tokens de prueba (válidos, vencidos, sin `exp`, de otra clave, `HS256`, sin firma o alterados), firmados con `TestRsaKeys`.
- `ProbeController` (`src/test/java/turnos/config/`): `GET /api/probe`, un endpoint protegido que existe solo en los tests que lo importan (`@TestComponent`). Sirve para probar la seguridad mientras no haya endpoints protegidos reales.
- `FakeHttpServer` (`src/test/java/turnos/`): servidor HTTP del JDK en un puerto aleatorio para simular sistemas externos. Cola de respuestas por ruta (la última se repite), demoras y registro de los requests. `respondTo(ruta, función)` arma la respuesta según el request, cuando depende de la consulta (desde T13). Lo usan los tests de catálogo y de la cátedra.
- `FakeCatedraServer` (`src/test/java/turnos/catedra/`): cátedra simulada sobre `FakeHttpServer` (`http()` da acceso a las respuestas por ruta). Por defecto responde un login técnico exitoso. `respondToListings` contesta el listado de reservas según el paciente, `listings()` da los pedidos recibidos y `appointment(...)` arma una reserva con el formato real (desde T13).
- Respuestas reales de la cátedra en `src/test/resources/catedra/` (limpias), leídas del classpath por los tests.
- `ControllableProcessRepository` (`src/test/java/turnos/reservation/`, se importa su `Configuration`): la base real, que falla al guardar a pedido, cuenta lo que guarda y las búsquedas de vencidos, las puede demorar, y avisa después de una lectura por dueño o de una búsqueda. Lo usan `PhoneSubmissionKafkaIntegrationTest`, `ReservationProcessStatusIntegrationTest`, `DatabaseDownStatusQueryIntegrationTest` (que también prueba el listado de T10 con la base en pausa), `OverdueSweepIntegrationTest`, `DatabaseDownOverdueSweepIntegrationTest` y `ReconciliationIntegrationTest`.
- Pausar Postgres en un test (`DatabaseDownKafkaIntegrationTest`, `DatabaseDownStatusQueryIntegrationTest`): una base pausada no cierra las conexiones. Hikari entrega sin comprobar una conexión usada hace menos de 500 ms, y con el límite de espera en 0 esa lectura no termina nunca. Por eso esos tests esperan 1 s justo antes de pausar si quieren que falle al pedir la conexión, y conviene ponerles un tiempo máximo (`@Timeout`).
- Dobles de test escritos a mano: `ScriptedLoginClient`, `MutableClock` (`src/test/java/turnos/`, público), `FakePasswordHasher`, `InMemoryUserRepository`.
- Dos suites (decisión 010). La normal (`./mvnw test`) simula todo y nunca lee el `.env`. La E2E vive en `src/test/java/e2e/` (fuera de `turnos`, con `classes = TurnosServiceApplication.class`), lleva `@Tag("e2e")`, la excluye Surefire por defecto y la corre el perfil `-Pe2e`, que lee el `.env`; sin credenciales se saltea. Antes de cualquier llamada a la cátedra real se le confirma al usuario qué requests se harán.
- Integración con la app completa: clases `*IntegrationTest` con `@SpringBootTest(webEnvironment = RANDOM_PORT)` y `RestTestClient`. Las que crean procesos de reserva borran `reservation_processes` antes que `users` (la clave foránea no deja borrar un usuario con procesos), como `ReservationProcessIntegrationTest`; ahí el hold y la confirmación simulados usan el mismo vencimiento.
- Concurrencia en un caso de uso: un repositorio en memoria que guarda y devuelve **copias**, como la base, para que cada operación trabaje sobre su propia lectura y aparezcan las carreras reales (`CopyingReservationProcessRepository`, en el paquete de los tests de casos de uso de `reservation`, junto con `InMemoryProcessedEventRepository`). Con el mismo objeto compartido, el modelo esconde la carrera. Una transacción real se prueba con `@DataJpaTest` sin su transacción por defecto (`@Transactional(propagation = NOT_SUPPORTED)`, como `SpringTransactionRunnerAdapterTest`).
- E2E: `E2ECredentials` (`src/test/java/e2e/`) decide si hay credenciales en el `.env` (lo lee `E2EEnvFile`); la usan `FreeSlotsE2ETest` y `ReservationProcessE2ETest`. El profesional ya no es fijo (TASK-11 de T13): `E2EProfessional` lee el snapshot de la cátedra con el JWT técnico de la app, toma uno habilitado de una categoría habilitada y el primer día desde mañana (hasta 14 días, 20 consultas) con los turnos libres que necesita el recorrido, y hace que el catálogo simulado responda con él. `E2EProfessionalTest` lo prueba sin cátedra, en la suite normal. `E2EKafka` enciende el consumo solo con `TURNOS_E2E_KAFKA_CONSUMER_GROUP` (terminada en `-e2e`) y solo lo usa `ReservationProcessE2ETest`: dos E2E con el mismo consumer group se repartirían el pedido. Este último crea un hold real en un turno libre, lo confirma, espera el pedido de teléfono por Kafka si la variable está (pasa completo desde el 2026-11-06), informa un teléfono de mentira con formato válido (T06; publica en el topic propio de la cuenta), espera `CONFIRMED` hasta 60 s con `GET` del proceso (T09 y T08), cancela con T11 (una reserva confirmada no vence sola) y espera el evento de cancelación. Al terminar siempre intenta cancelar directo en la cátedra, como limpieza: si la cátedra no lo permite, imprime un aviso con el id del proceso y no falla (D9 de T04). Si la cátedra confirma después de esa espera, la reserva queda y hay que cancelarla a mano. `aUserAbandonsAHeldProcessAndBlocksAnotherFreeSlot` no depende de Kafka: bloquea, abandona con T11 y bloquea otro turno; deja dos turnos tomados hasta 10 minutos, y se corre solo con `-Dtest='ReservationProcessE2ETest#aUserAbandonsAHeldProcessAndBlocksAnotherFreeSlot'`. Cada corrida deja una reserva `PHONE_PENDING` que vence a los 10 minutos, en el profesional y el día elegidos. El modo automático de Claude Code bloquea las escrituras a la cátedra y el `!` no llegó a correr `-Pe2e`: el usuario corre el E2E en su terminal y Claude lee `target/surefire-reports/`.
- Capa web: `@WebMvcTest` del controller con `@Import({TestSecurityConfiguration.class, ...})` y el service simulado con `@MockitoBean`.
- Para contar los tests de una corrida, usar los reportes XML (`target/surefire-reports/TEST-*.xml`): el resumen `.txt` de Surefire no suma los tests de las clases `@Nested`.
- Práctica acordada: después de que un test pasa, una prueba en negativo (romper el código a propósito, ver que el test falla, restaurar el archivo y comprobar el hash) para demostrar que el test detecta el error. Los errores que pueden taparse entre sí (por ejemplo, un mapper que pierde un campo y una migración con otro valor por defecto) se prueban en rondas separadas.
- `./mvnw clean test` para el conteo final y después de renombrar o borrar archivos: sin `clean` pueden quedar clases y reportes viejos en `target/`.
