| **NOMBRE** | T01 — Registrar usuario |
| --- | --- |
| **Actor principal** | Aplicación KMP |
| **Actor secundario** | Ninguno |
| **Descripción** | Crea una cuenta de usuario final en el servicio de turnos a partir de los datos de registro que define el enunciado (`login`, `password`, `firstName`, `lastName`, `email`, `langKey` y, opcionalmente, `imageUrl`), con los mismos datos y el mismo comportamiento observable que un usuario de JHipster, sin que sea necesario usarlo. El usuario queda activo de inmediato, sin verificación por correo, y con rol de usuario común (el rol ADMINISTRADOR no se asigna por este medio). Es un endpoint expresamente público, ya que se usa antes de tener sesión. No emite JWT: para autenticarse, el usuario debe iniciar sesión después (T02). |
| **Alcance** | Servicio de turnos y reservas |
| **Precondición** | - Ninguna. Es un endpoint expresamente público: no requiere sesión. |
| **Flujo** | **1-** El usuario completa el formulario de registro en la app (`login`, `password`, `firstName`, `lastName`, `email`, `langKey` y, opcionalmente, `imageUrl`) y la app lo envía al servicio de turnos.<br>**2-** El servicio valida el formato y la obligatoriedad de los campos recibidos: `login` de 3 a 50 caracteres (letras, números y los que admite el login de JHipster), `password` de 4 a 100, `firstName` y `lastName` de 2 a 50, `email` válido de 5 a 254 caracteres y `langKey` de 2 a 10; `imageUrl` es el único opcional. Ignora y descarta cualquier campo que intente fijar datos administrados por el backend, como identificador, estado de activación, autoridades o auditoría.<br>**3-** Verifica que el `login` no esté ya registrado.<br>**4-** Verifica que el `email` no esté ya registrado.<br>**5-** Genera el hash de la contraseña con un mecanismo criptográfico adecuado; nunca se guarda en texto plano.<br>**6-** Crea el usuario, activo, con rol de usuario común, y el resto de los campos administrados por el backend (id, estado de activación, autoridades y auditoría).<br>**7-** Devuelve `201` con los datos públicos del usuario (sin la contraseña), para que la app confirme el registro y proponga iniciar sesión. |
| **Flujo alternativo** | **2.1, Falta un campo obligatorio o tiene formato inválido (`login`, `password`, `firstName`, `lastName`, `email` o `langKey`):** responde `400` con un código funcional y el detalle de los campos inválidos, sin consultar la base; termina.<br>**3.1, El `login` ya está registrado:** responde `400` con un código funcional y termina.<br>**4.1, El `email` ya está registrado:** responde `400` con un código funcional y termina.<br>**6.1, Falla la persistencia:** se registra el error y se responde un error del servidor (`500`) sin exponer detalles internos; termina. |
| **Postcondición** | **- Éxito:** existe un nuevo usuario, activo, con la contraseña hasheada, rol de usuario común y los campos de sistema asignados por el backend. No se emitió ningún JWT.<br>**- Fracaso:** no se crea ningún usuario y, si fue un error del servidor, queda registrado. |

| **NOMBRE** | T02 — Iniciar sesión |
| --- | --- |
| **Actor principal** | Aplicación KMP |
| **Actor secundario** | Ninguno |
| **Descripción** | Autentica a un usuario ya registrado (T01) con su `login` y `password`, y emite un JWT propio del servicio de turnos, que la app usará durante la sesión para consumir las APIs protegidas de turnos y de catálogo. El JWT lleva el identificador estable del usuario y su rol. Es un endpoint expresamente público. |
| **Alcance** | Servicio de turnos y reservas |
| **Precondición** | - El usuario ya está registrado (T01) y su cuenta está activa. |
| **Flujo** | **1-** El usuario completa `login` y `password` en la app y la app los envía al servicio de turnos.<br>**2-** El servicio valida que `login` y `password` estén presentes.<br>**3-** Busca el usuario por `login`.<br>**4-** Verifica que la contraseña recibida coincida con el hash almacenado.<br>**5-** Genera y firma un JWT del servicio de turnos, con el identificador estable del usuario y su rol (usuario común o, si corresponde, ADMINISTRADOR), y una vigencia definida por la configuración del servicio.<br>**6-** Devuelve `200` con el JWT, para que la app lo use en las siguientes solicitudes. |
| **Flujo alternativo** | **2.1, Falta `login` o `password`:** responde `400` con un código funcional y termina.<br>**3.1, No existe un usuario con ese `login`:** responde `401` con un mensaje genérico de credenciales inválidas, sin indicar si el problema fue el `login` o la contraseña, y termina.<br>**4.1, La contraseña no coincide:** responde `401` con el mismo mensaje genérico que 3.1, y termina.<br>**5.1, Falla la generación o la firma del JWT:** se registra el error y se responde un error del servidor (`500`) sin exponer detalles internos; termina. |
| **Postcondición** | **- Éxito:** la app dispone de un JWT vigente, asociado al usuario, para usar en T03 en adelante y en las consultas que turnos hace a catálogo (C06) en su nombre.<br>**- Fracaso:** no se emite ningún JWT y no se modifica nada. |

| **NOMBRE** | T03 — Consultar turnos libres de un profesional |
| --- | --- |
| **Actor principal** | Aplicación KMP |
| **Actor secundario** | Servicio de catálogo y sincronización (C06); Servicio de la cátedra (soporte, REST de ocupaciones) |
| **Descripción** | Calcula, para un profesional y una fecha elegidos por el usuario, los turnos libres, combinando los horarios semanales vigentes que informa el servicio de catálogo con las ocupaciones (reservas confirmadas y bloqueos activos) que informa la cátedra. Prioriza siempre la consulta en vivo a la cátedra; si no está disponible, recurre a un caché propio de la última consulta exitosa para ese mismo profesional y esa misma fecha, y lo señala como tal. Requiere sesión iniciada. |
| **Alcance** | Servicio de turnos y reservas |
| **Precondición** | - El usuario tiene sesión iniciada (T02) y la app dispone de un JWT vigente.<br>- X01 completado (JWT técnico de la cátedra disponible). |
| **Flujo** | **1-** El usuario elige un profesional (de C05) y una fecha, y la app solicita los turnos libres de ese profesional en esa fecha al servicio de turnos, enviando el JWT del usuario.<br>**2-** Turnos valida el JWT del usuario (firma, vigencia y permisos).<br>**3-** Turnos valida los parámetros recibidos (`professionalId` numérico, `date` con formato válido y no anterior a la fecha actual).<br>**4-** Turnos solicita al servicio de catálogo los horarios semanales vigentes del profesional (C06), reenviando el JWT del usuario.<br>**5-** Turnos solicita a la cátedra las ocupaciones del profesional para esa fecha (`GET /api/appointment-occupancies` con `from` y `to` iguales a la fecha), con el JWT técnico.<br>**6-** Turnos guarda (o reemplaza) en su caché la entrada para ese `professionalId` y esa `date`, con las ocupaciones recibidas y la fecha y hora en que se obtuvieron (`dataAsOf`).<br>**7-** Turnos determina el día de la semana de la fecha y toma los horarios semanales habilitados de ese día; para cada uno, genera los turnos posibles a partir de `startTime`, de a `slotDurationMinutes`, incluyendo solo los que terminan en o antes de `endTime`, y descarta los que ya comenzaron si la fecha es la de hoy.<br>**8-** Turnos descarta los turnos que aparecen en las ocupaciones con estado `CONFIRMED` o `HELD` (ambos se tratan como ocupados; la cátedra no informa a quién pertenece cada uno).<br>**9-** Turnos devuelve la lista de turnos libres restantes, ordenados por hora de inicio, cada uno con `professionalId`, `date`, `startTime` y `durationMinutes`. |
| **Flujo alternativo** | **2.1, El JWT del usuario falta, es inválido, está vencido o no tiene permisos:** responde `401` o `403` sin datos y termina.<br>**3.1, `professionalId` falta o no es numérico, o `date` tiene formato inválido o es anterior a la fecha actual:** responde `400` con un código funcional y termina.<br>**4.1, Catálogo responde `401` o `403` al JWT reenviado:** se registra como error de integración interna, se responde un error del servidor (`500`) a la app y termina.<br>**4.2, Catálogo responde `404` (profesional inexistente):** responde `404` con un código funcional a la app y termina.<br>**4.3, Catálogo no está disponible (timeout, `503`, corte de conexión):** se reintenta con espera creciente y un máximo de intentos; agotados, se responde `503` (catálogo no disponible) sin consultar a la cátedra, y termina.<br>**4.4, El profesional está deshabilitado (`enabled` en falso):** responde `409` con un código funcional (`PROFESSIONAL_DISABLED`), igual que T04 (5.4), sin consultar a la cátedra; termina.<br>**4.5, El profesional no tiene ningún horario semanal habilitado para el día de la semana de la fecha:** se devuelve una lista vacía de turnos libres con un mensaje indicando que el profesional no atiende ese día (`200`), sin consultar a la cátedra; termina.<br>**5.1, La cátedra responde `401` (JWT técnico vencido o rechazado):** se ejecuta X01 y se retoma en el paso 5, una sola vez.<br>**5.2, La cátedra responde `403` `STUDENT_INTEGRATION_NOT_FOUND`:** error de configuración; se registra y se responde `503` (servicio degradado) sin exponer detalles; termina.<br>**5.3, Timeout, corte de conexión, `503` o `500` de la cátedra:** se reintenta con espera creciente y un máximo de intentos. Agotados los intentos, turnos busca en su caché una entrada para ese mismo `professionalId` y esa misma `date`: si existe y no supera la antigüedad máxima configurada, la usa para completar los pasos 7 a 9 en lugar de la respuesta en vivo, y marca la respuesta como proveniente del caché (`stale: true`, con el `dataAsOf` guardado); si existe pero supera esa antigüedad, no la usa y la elimina del caché; si no hay ninguna entrada utilizable (no existía o fue descartada por antigua), se responde 503 (los turnos no pudieron calcularse) y termina.<br>**8.1, No queda ningún turno libre ese día (todos ocupados o ya comenzados):** se devuelve una lista vacía con un mensaje indicando que no quedan turnos libres para esa fecha (`200`). |
| **Postcondición** | - No se modifica ningún dato de negocio (el caché es un dato auxiliar de turnos, no una entidad del dominio).<br>**- Éxito:** la app dispone de los turnos libres del profesional para esa fecha (en vivo o, si se indica, desde el caché); el resultado puede cambiar en la siguiente consulta o al intentar bloquear un turno (T04), que siempre valida en vivo.<br>**- Fracaso:** no se modifica ningún dato de negocio (a lo sumo se elimina del caché una entrada vencida); el error queda registrado cuando corresponde. |

| **NOMBRE** | T04 — Bloquear turno temporalmente (crear hold) |
| --- | --- |
| **Actor principal** | Aplicación KMP |
| **Actor secundario** | Servicio de catálogo y sincronización (C06); Servicio de la cátedra (soporte, REST de holds) |
| **Descripción** | A partir de un turno concreto que el usuario eligió (tras T03), inicia un proceso de reserva pidiendo a la cátedra un bloqueo temporal (hold) sobre ese turno, para evitar que otro lo tome mientras el usuario confirma. Turnos revalida el turno contra los horarios semanales vigentes de catálogo antes de pedir el hold, y conserva localmente el proceso creado, asociado al usuario. El bloqueo es temporal: su vigencia real la determina `expiresAt` que fija la cátedra. Un usuario puede tener a lo sumo un proceso de reserva abierto a la vez. |
| **Alcance** | Servicio de turnos y reservas |
| **Precondición** | - El usuario tiene sesión iniciada (T02) y la app dispone de un JWT vigente.<br>- X01 completado (JWT técnico de la cátedra disponible). |
| **Flujo** | **1-** El usuario elige un turno concreto (profesional, fecha y hora) de los que vio en T03, y la app lo envía al servicio de turnos, con el JWT del usuario.<br>**2-** Turnos valida el JWT del usuario (firma, vigencia y permisos).<br>**3-** Turnos valida los parámetros recibidos (`professionalId` numérico, `date` y `startTime` con formato válido, y que el turno no sea anterior al momento actual). Cierra por vencimiento, con el margen de seguridad, los procesos del usuario en `HELD` o `WAITING_FOR_PHONE` que ya vencieron, y verifica que no le quede ninguno abierto (`HELD`, `WAITING_FOR_PHONE` o `PHONE_SUBMITTED`).<br>**4-** Turnos solicita al servicio de catálogo los horarios semanales vigentes del profesional (C06), reenviando el JWT del usuario, y verifica que el turno elegido sea uno de los turnos de un horario semanal habilitado para ese día: que empiece a una hora que resulte de sumar un múltiplo de `slotDurationMinutes` a `startTime` y que termine en o antes de `endTime`.<br>**5-** Turnos determina el identificador estable del usuario (`externalPatientId`) y solicita a la cátedra crear el hold (`POST /api/appointment-holds`) con `professionalId`, `date`, `startTime` y `externalPatientId`, usando el JWT técnico.<br>**6-** La cátedra concede el hold y devuelve `holdId`, `reservationProcessId`, `status` (`HELD`) y `expiresAt`.<br>**7-** Turnos crea localmente un nuevo proceso de reserva en estado `HELD`, asociado al usuario, con `holdId`, `reservationProcessId`, `professionalId`, `date`, `startTime`, `expiresAt` y datos descriptivos del profesional al momento del bloqueo (nombre, categoría), a título histórico.<br>**8-** Turnos devuelve a la app el proceso creado (`reservationProcessId`, `status`, `expiresAt`), para que el usuario continúe con la confirmación inicial (T05). |
| **Flujo alternativo** | **2.1, El JWT del usuario falta, es inválido, está vencido o no tiene permisos:** responde `401` o `403` sin datos y termina.<br>**3.1, `professionalId` falta o no es numérico, o `date`/`startTime` tienen formato inválido, o el turno es anterior al momento actual:** responde `400` con un código funcional y termina.<br>**3.2, El usuario ya tiene un proceso abierto:** responde `409` con un código funcional (`OPEN_PROCESS_EXISTS`) e incluye los datos de ese proceso (`reservationProcessId`, estado y `expiresAt`), para que la app lo lleve a "Mis reservas" a continuarlo o cancelarlo (T11); termina. <br>**4.1, Catálogo responde `404` (profesional inexistente):** responde `404` con un código funcional y termina.<br>**4.2, El turno elegido no cae en ningún horario habilitado según la copia local de catálogo:** responde `400` con un código funcional propio, sin llamar a la cátedra, y termina.<br>**4.3, Catálogo no está disponible (timeout, `503`, corte de conexión):** se reintenta con espera creciente y un máximo de intentos; agotados, se responde `503` (no puede iniciarse la operación) y termina, sin llamar a la cátedra.<br>**4.4, Catálogo responde 401 o 403 al JWT reenviado:** se registra como error de integración interna, se responde un error del servidor (500) a la app y termina, sin llamar a la cátedra.<br>**4.5, El profesional está deshabilitado (`enabled` en falso):** responde `409` con un código funcional (`PROFESSIONAL_DISABLED`), igual que 5.4 y que T03 (4.4), sin llamar a la cátedra; termina.<br>**5.1, La cátedra responde `401` (JWT técnico vencido o rechazado):** se ejecuta X01 y se retoma en el paso 5, una sola vez.<br>**5.2, La cátedra responde `403` `STUDENT_INTEGRATION_NOT_FOUND`:** error de configuración; se registra y se responde `503` sin exponer detalles; termina.<br>**5.3, La cátedra responde `404` `PROFESSIONAL_NOT_FOUND` (pese a la validación de 4.1, pudo desincronizarse justo antes):** se registra y se responde `404` con un código funcional; termina.<br>**5.4, La cátedra responde `400` `PROFESSIONAL_DISABLED`:** se responde `409` con un código funcional indicando que el profesional ya no acepta turnos; termina.<br>**5.5, La cátedra responde `400` `INVALID_SLOT` (pese a la validación de 4.2, pudo desincronizarse justo antes):** se responde `400` con un código funcional; termina.<br>**5.6, La cátedra responde `409` `SLOT_ALREADY_RESERVED`:** el turno ya está confirmado por otra reserva; se responde `409` con un código funcional indicando que el turno ya no está disponible; termina.<br>**5.7, La cátedra responde `409` `SLOT_ALREADY_HELD`:** hay otro bloqueo activo sobre el mismo turno; se responde `409` con un código funcional equivalente al de 5.6; termina.<br>**5.8, Timeout, corte de conexión, `503` o `500` de la cátedra:** si es seguro que la cátedra no procesó el pedido (no se pudo conectar, venció el tiempo de conexión o respondió `503`), se reintenta con espera creciente y un máximo de intentos. Si pudo haberlo procesado (venció el tiempo de espera de la respuesta, la conexión se cortó durante la respuesta o respondió `500`), no se reintenta, porque el hold podría haberse creado, y se registra. En los dos casos, sin hold, se responde `503` (el bloqueo no pudo crearse) y termina, sin crear ningún proceso local; si el hold se creó, vence solo, como en 7.1.<br>**7.1, El hold se creó en la cátedra pero falla la persistencia local:** Se registra el error como crítico (existe un hold huérfano, sin rastro local). Turnos responde `500` con un código funcional, incluyendo el `expiresAt` que ya había recibido de la cátedra en el paso 6 (aunque no haya podido guardarlo) y el encabezado HTTP `Retry-After`, para indicarle a la app hasta cuándo, aproximadamente, el turno seguirá retenido y no conviene reintentar antes de esa hora. No hay recuperación automática de este caso: se resuelve solo, cuando el hold vence del lado de la cátedra (ver T13). |
| **Postcondición** | **- Éxito:** existe un hold vigente en la cátedra y un proceso de reserva local en estado `HELD`, asociado al usuario, con su `expiresAt`; el usuario puede confirmarlo (T05) antes de que venza.<br>**- Fracaso:** no se modifica nada localmente (salvo 7.1, donde puede quedar un hold sin registrar que vence solo; el estado del turno en la cátedra queda como ella lo haya dejado. |

| **NOMBRE** | T05 — Confirmar reserva (confirmación inicial) |
| --- | --- |
| **Actor principal** | Aplicación KMP |
| **Actor secundario** | Servicio de la cátedra (soporte, REST de confirmación de holds) |
| **Descripción** | Confirma ante la cátedra el bloqueo temporal que el usuario creó en T04, usando el nombre y apellido de su perfil como datos del paciente. La cátedra inicia una reserva `PHONE_PENDING` y publica un pedido de información adicional (el teléfono), que se procesa por Kafka en T07. Es el primer paso de la confirmación; el proceso queda pendiente hasta que se completa el intercambio asincrónico. |
| **Alcance** | Servicio de turnos y reservas |
| **Precondición** | - El usuario tiene sesión iniciada (T02) y la app dispone de un JWT vigente.<br>- Existe un proceso de reserva local en estado `HELD`, creado por T04 y asociado a ese usuario, con `holdId`, `reservationProcessId` y `expiresAt` vigentes.<br>- X01 completado. |
| **Flujo** | **1-** El usuario confirma el turno bloqueado y la app envía la confirmación al servicio de turnos, con el JWT del usuario y el `reservationProcessId` del proceso a confirmar.<br>**2-** Turnos valida el JWT del usuario (firma, vigencia y permisos) y verifica que el proceso indicado exista y pertenezca a ese usuario.<br>**3-** Turnos verifica localmente que el proceso está en estado `HELD` y que su `expiresAt` no venció, y toma `firstName` y `lastName` del perfil del usuario como `patientFirstName` y `patientLastName`.<br>**4-** Turnos solicita a la cátedra confirmar el hold (`POST /api/appointment-holds/{holdId}/confirm`) con `externalPatientId`, `patientFirstName` y `patientLastName`, usando el JWT técnico.<br>**5-** La cátedra crea una reserva `PHONE_PENDING`, publica `AdditionalInformationRequested` y responde con `reservationProcessId`, `status` (`WAITING_FOR_PHONE`) y `expiresAt`, que es el mismo del hold: confirmar no extiende el vencimiento.<br>**6-** Turnos actualiza localmente el proceso a `WAITING_FOR_PHONE`, con el `expiresAt` que informa la cátedra.<br>**7-** Turnos devuelve a la app el estado actualizado, para que el usuario sepa que debe informar el teléfono (T06) antes de que venza. |
| **Flujo alternativo** | **2.1, El JWT del usuario falta, es inválido, está vencido o no tiene permisos:** responde `401` o `403` sin datos y termina.<br>**2.2, El proceso indicado no existe o no pertenece a ese usuario:** responde `404` (sin distinguir un caso del otro) y termina.<br>**3.1, El proceso no está en estado `HELD` (ya avanzó a esperar el teléfono, ya se envió el teléfono, o fue confirmado, cancelado o expiró):** responde `409` con un código funcional indicando el estado actual y termina.<br>**3.2, El `expiresAt` local, más un margen de seguridad (parámetro configurable, a definir en el diseño), ya venció:** se marca localmente el proceso como `EXPIRED` (si no lo estaba) y se responde `409` con un código funcional (`HOLD_EXPIRED`), sin llamar a la cátedra; el usuario debe repetir T04.<br>**4.1, La cátedra responde `401` (JWT técnico vencido o rechazado):** se ejecuta X01 y se retoma en el paso 4, una sola vez.<br>**4.2, La cátedra responde `403` `STUDENT_INTEGRATION_NOT_FOUND`:** error de configuración; se registra y se responde `503` sin exponer detalles; termina.<br>**4.3, La cátedra responde `404` `HOLD_NOT_FOUND`:** si el `expiresAt` local ya pasó, el hold venció y la cátedra ya no lo encuentra (un hold vencido responde así): se sigue como 4.4. Si todavía no pasó, se registra y se responde `404` con un código funcional; termina.<br>**4.4, La cátedra responde `404` `HOLD_EXPIRED`, o `404` `HOLD_NOT_FOUND` con el `expiresAt` local ya pasado (4.3):** se marca localmente el proceso como `EXPIRED` y se responde `409` con un código funcional (`HOLD_EXPIRED`); el usuario debe repetir T04.<br>**4.5, La cátedra responde `403` `HOLD_OWNER_MISMATCH`:** no debería ocurrir, ya que ambos backends comparten la misma cuenta técnica; se registra como error grave y se responde `500`; termina.<br>**4.6, La cátedra responde `400` `EXTERNAL_PATIENT_MISMATCH`:** el paciente no coincide con el guardado en el hold; se registra y se responde `409` con un código funcional; termina.<br>**4.7, La cátedra responde `409` `RESERVATION_PROCESS_ALREADY_CONFIRMED`:** el proceso ya había sido confirmado antes (posible reintento de la app); turnos actualiza su copia local si estaba desactualizada y responde con el estado actual, sin tratarlo como error.<br>**4.8, La cátedra responde `404` `PROFESSIONAL_NOT_FOUND`, `400` `INVALID_SLOT` o `409` `SLOT_ALREADY_RESERVED` (la matriz de errores los admite también para confirmar):** se registra y se responde con el código funcional correspondiente, igual que en T04 (5.3 a 5.6); termina.<br>**4.9, Timeout, corte de conexión, `503` o `500` de la cátedra:** se reintenta con espera creciente y un máximo de intentos; agotados, se responde `503`, el proceso local permanece en `HELD` (no se sabe si la cátedra llegó a procesarlo) y se marca para reconciliar (T13). Si el pedido de teléfono llega por Kafka (T07), el proceso avanza solo.<br>**6.1, Falla la persistencia local tras la confirmación de la cátedra:** se registra el error como crítico (la cátedra ya avanzó el proceso pero turnos no lo reflejó) y se marca para reconciliar (T13). |
| **Postcondición** | **- Éxito:** el proceso queda en `WAITING_FOR_PHONE`, tanto local como en la cátedra, con el mismo `expiresAt` del hold; el usuario debe informar el teléfono (T06) antes de que venza.<br>**- Fracaso:** el proceso permanece en su estado previo, salvo 3.2 y 4.4, que lo dejan en `EXPIRED`; el turno puede perderse si el hold venció. |

| **NOMBRE** | T06 — Informar teléfono |
| --- | --- |
| **Actor principal** | Aplicación KMP |

| **NOMBRE** | T07 — Procesar solicitud de información adicional |
| --- | --- |
| **Actor principal** | Servicio de la cátedra (iniciador: aviso `AdditionalInformationRequested` por Kafka) |
| **Actor secundario** | Ninguno |
| **Descripción** | Recibe el pedido de información adicional que la cátedra publica tras confirmar un hold (T05), lo valida, lo correlaciona con el proceso de reserva local y guarda el `requestEventId` que T06 necesita para responder. No interactúa con el usuario: es un procesamiento interno, silencioso, del lado de turnos. |
| **Alcance** | Servicio de turnos y reservas |
| **Precondición** | - X01 completado (turnos está consumiendo el topic `alumnos.turnos.acciones.{groupId}`). |
| **Flujo** | **1-** Turnos recibe un mensaje `AdditionalInformationRequested` del topic `alumnos.turnos.acciones.{groupId}` (`eventId`, `reservationProcessId`, `holdId`, `requiredField`, `message`, `expiresAt`, `occurredAt`, `schemaVersion`).<br>**2-** Valida el mensaje (campos requeridos presentes, `schemaVersion` igual a 1, y que `requiredField` sea uno que turnos sabe procesar, `PHONE_NUMBER`).<br>**3-** Verifica que el `eventId` no haya sido procesado antes.<br>**4-** Busca localmente el proceso de reserva por `reservationProcessId`, y verifica que el `holdId` recibido coincida con el guardado.<br>**5-** Verifica que el proceso está en `WAITING_FOR_PHONE` o en `HELD` (el evento puede llegar antes de que T05 termine de actualizar el estado local).<br>**6-** Guarda localmente el `requestEventId` (el `eventId` de este mensaje),  actualiza el `expiresAt` del proceso con el valor recibido y, si el proceso estaba en `HELD`, lo pasa a `WAITING_FOR_PHONE` (el pedido prueba que la cátedra ya confirmó el hold).<br>**7-** Registra el `eventId` como procesado y confirma el offset del mensaje en Kafka. |
| **Flujo alternativo** | **2.1, El mensaje es inválido (campos requeridos ausentes, `schemaVersion` desconocida) o `requiredField` no es `PHONE_NUMBER`:** se descarta, se registra el error o la limitación, y se confirma el offset (termina); no hay forma de recuperar este aviso puntual.<br>**3.1, El `eventId` ya fue procesado:** no se repite ningún efecto, se confirma el offset y termina.<br>**4.1, No existe un proceso local con ese `reservationProcessId`:** se registra como evento huérfano, se confirma el offset (no hay nada propio a lo que asociarlo) y termina.<br>**4.2, El `holdId` del evento no coincide con el guardado en el proceso local:** se registra como inconsistencia, se confirma el offset (no se puede actuar con seguridad) y termina.<br>**5.1, El proceso no está en `HELD` ni `WAITING_FOR_PHONE` (ya expiró, ya se envió el teléfono, fue cancelado, o llegó duplicado por otro camino):** se registra, se confirma el offset (el estado ya avanzó, no corresponde retroceder) y termina.<br>**6.1, Falla la persistencia local:** se reintenta con espera creciente y un máximo de intentos; agotados, se registra el error y **no** se confirma el offset, para que Kafka reentregue el mensaje más adelante. |
| **Postcondición** | **- Éxito:** el proceso tiene guardado el `requestEventId` (que T06 necesita para publicar su respuesta), su `expiresAt` actualizado y, si venía de `HELD`, queda en `WAITING_FOR_PHONE`.<br>**- Fracaso:** el proceso permanece como estaba; en los casos irrecuperables (2.1, 4.1, 4.2, 5.1) no hay reintento posible sobre este evento puntual. |

| **NOMBRE** | T08 — Procesar resultado de la reserva |
| --- | --- |
| **Actor principal** | Servicio de la cátedra (iniciador: `AppointmentConfirmed`, `AdditionalInformationRejected`, `AppointmentProcessExpired`, `AppointmentProcessInvalid` o `AppointmentCancelled` por Kafka) |
| **Actor secundario** | Ninguno |
| **Descripción** | Recibe y procesa el resultado que la cátedra publica sobre un proceso de reserva, cualquiera de los cinco tipos posibles, y actualiza el estado local en consecuencia: confirma la reserva, vuelve a pedir el teléfono si fue rechazado, marca el proceso como vencido, lo marca para reconciliar si quedó inconsistente, o lo marca como cancelado. Un evento tardío nunca reabre un proceso que ya llegó a un estado final; la única excepción es la cancelación de una reserva confirmada, que sí es una transición válida. |
| **Alcance** | Servicio de turnos y reservas |
| **Precondición** | - X01 completado (turnos está consumiendo el topic `alumnos.turnos.acciones.{groupId}`). |
| **Flujo** | **1-** Turnos recibe un mensaje del topic `alumnos.turnos.acciones.{groupId}`, de alguno de los cinco tipos.<br>**2-** Valida el mensaje (campos requeridos según su tipo, `schemaVersion` igual a 1). Para `AppointmentCancelled` no se exigen `requestEventId` ni `reservationId`, que pueden faltar si se canceló antes de confirmar.<br>**3-** Verifica que el `eventId` no haya sido procesado antes.<br>**4-** Busca localmente el proceso por `reservationProcessId`, y verifica que el `holdId` coincida.<br>**5-** Aplica el efecto según el tipo de evento:<br>&nbsp;&nbsp;**-** `AppointmentConfirmed`: crea o actualiza localmente la reserva confirmada, con `reservationId`, `professionalId`, `date` y `startTime`, guarda la fecha de confirmación (`occurredAt`) y marca el proceso como `CONFIRMED`.<br>&nbsp;&nbsp;**-** `AdditionalInformationRejected`: vuelve el proceso a `WAITING_FOR_PHONE`, actualiza su `expiresAt` con el recibido, y guarda `reason` para mostrárselos al usuario; el `requestEventId` guardado no cambia, sigue siendo válido para el próximo intento (T06).<br>&nbsp;&nbsp;**-** `AppointmentProcessExpired`: marca el proceso como `EXPIRED`.<br>&nbsp;&nbsp;**-** `AppointmentProcessInvalid`: marca el proceso como `INVALID`, pendiente de que T13 lo reconcilie por REST.<br>&nbsp;&nbsp;**-** `AppointmentCancelled`: marca la reserva o el proceso como `CANCELLED`, guardando `reason` y `occurredAt` (`reason` puede ser `null`).<br>**6-** Registra el `eventId` como procesado y confirma el offset del mensaje en Kafka. |
| **Flujo alternativo** | **2.1, El mensaje es inválido (campos requeridos ausentes, `schemaVersion` desconocida) o el `eventType` no es ninguno de los cinco reconocidos:** se descarta, se registra el error, se confirma el offset y termina.<br>**3.1, El `eventId` ya fue procesado:** no se repite ningún efecto, se confirma el offset y termina.<br>**4.1, No existe un proceso local con ese `reservationProcessId`:** se registra como evento huérfano, se confirma el offset y termina.<br>**4.2, El `holdId` del evento no coincide con el guardado en el proceso local:** se registra como inconsistencia, se confirma el offset y termina.<br>**5.1, El proceso ya está en un estado final (`CONFIRMED`, `EXPIRED`, `CANCELLED` o `INVALID`):** no se reabre; se ignora el efecto del mensaje, aunque se registra el `eventId` como procesado, se confirma el offset y termina. Excepción: si el mensaje es `AppointmentCancelled` y el estado local es `CONFIRMED`, sí se aplica (una reserva confirmada puede cancelarse) y se continúa en el paso 6.<br>**5.2, Falla la persistencia al aplicar el efecto:** se reintenta con espera creciente y un máximo de intentos; agotados, se registra el error y **no** se confirma el offset, para que Kafka reentregue el mensaje más adelante. |
| **Postcondición** | **- Éxito:** el proceso refleja el resultado que indicó la cátedra: reserva creada y confirmada, vuelta a esperar teléfono, expirado, cancelado, o marcado para reconciliar.<br>**- Fracaso:** el proceso permanece en su estado previo; en los casos irrecuperables (2.1, 4.1, 4.2, 5.1) no hay reintento sobre este evento puntual. |

| **NOMBRE** | T11 — Cancelar reserva o proceso de reserva en curso |

| **Actor principal** | Aplicación KMP |
| **Actor secundario** | Servicio de la cátedra (soporte, REST de cancelación) |

| **NOMBRE** | T13 — Reconciliar y recuperar procesos pendientes |

| **Actor principal** | Tiempo (al arrancar el servicio, y luego a intervalos periódicos) |
| **Actor secundario** | Servicio de la cátedra (soporte, REST de listado de reservas) |
| **Descripción** | Verifica contra la cátedra el estado real de los procesos que quedaron en una situación ambigua (marcados explícitamente para reconciliar, o abiertos porque el servicio se reinició a mitad de camino), y corrige el estado local si difiere. Es la red de seguridad de todo el proceso de reserva, igual que C03 lo es para el catálogo. El caso del hold huérfano de T04 (7.1) queda fuera de alcance a propósito: la app nunca recibe el `reservationProcessId` cuando eso ocurre, así que no hay ningún flujo de usuario que quede roto ni nada que reconciliar desde su lado. El turno se autolimpia con el propio TTL del hold, del lado de la cátedra, y un reintento del usuario en ese lapso simplemente ve el turno momentáneamente no disponible (`SLOT_ALREADY_HELD`). Un barrido dedicado para adelantarse a ese vencimiento exigiría traer el listado completo de la cuenta técnica, sin poder filtrar por usuario, con una frecuencia cercana a la del propio TTL del hold — un costo que no se justifica frente al beneficio. |
| **Alcance** | Servicio de turnos y reservas |
| **Precondición** | - X01 completado. |
| **Flujo** | **1-** Tiempo dispara la reconciliación: al arrancar el servicio y luego a intervalos periódicos.<br>**2-** Turnos verifica que no haya otra reconciliación en curso.<br>**3-** Busca localmente los procesos a reconciliar: los marcados explícitamente como tales por T05, T06, T08, T09, T10, T11 o T12 y, solo en la ejecución de arranque, también cualquier proceso que haya quedado en `HELD`, `WAITING_FOR_PHONE` o `PHONE_SUBMITTED` (sobrevivió a un reinicio a mitad de camino).<br>**4-** Para cada uno, consulta a la cátedra su estado real (`GET /api/appointments`, filtrando por `externalPatientId` del usuario dueño y un rango de fechas que incluya la del turno), con el JWT técnico.<br>**5-** Compara el estado recibido con el local y lo actualiza si difiere, según la propia máquina de estados de turnos (`CONFIRMED`→`CONFIRMED`; `CANCELLED`→`CANCELLED`; `PHONE_PENDING`→`WAITING_FOR_PHONE`, salvo que el teléfono ya se haya informado localmente; `FAILED`→`EXPIRED`), guardando el `reservationId` y la fecha de confirmación (`confirmedAt`) cuando la cátedra los informa.<br>**6-** Si la cátedra no devuelve ningún registro para ese `reservationProcessId`: si el proceso local está en `HELD` y su `expiresAt`, más el margen de seguridad, no venció, se deja abierto (el listado de la cátedra muestra reservas, no holds); en cualquier otro caso se marca `EXPIRED`.<br>**7-** Registra el resultado de la reconciliación de cada proceso, haya cambiado o no. |
| **Flujo alternativo** | **2.1, Ya hay otra reconciliación en curso:** se omite esta ejecución y termina.<br>**4.1, La cátedra responde `401` (JWT técnico vencido):** se ejecuta X01 y se retoma en el paso 4, una sola vez.<br>**4.2, La cátedra no está disponible (timeout, `503`, corte de conexión):** se reintenta con espera creciente y un máximo de intentos; agotados, el proceso queda pendiente para el siguiente ciclo, sin cambios.<br>**5.1, El estado local ya coincide con el recibido:** no se modifica nada, se registra igual.<br>**7.1, Falla la persistencia al aplicar la corrección:** se registra el error, ese proceso queda pendiente para el siguiente ciclo, y se continúa con los demás. |
| **Postcondición** | **- Éxito:** los procesos reconciliados en este ciclo reflejan el estado real de la cátedra. Los que no pudieron reconciliarse permanecen marcados, a la espera del siguiente ciclo. |
